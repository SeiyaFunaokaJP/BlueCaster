# 断音与连接问题
{: .no_toc }

声音断续、卡顿或中断，连接失败，或者比特率低于预期？本页汇总了以往此类报告最终查明的原因。报告之前，你可以先排查这些常见原因；如果都不符合，本页也说明了需要提供哪些信息。

## 请先检查这些 {#checklist}

蓝牙与 Wi-Fi、无线鼠标和键盘、耳麦接收器以及房间里的其他所有蓝牙设备共用 2.4 GHz 频段。USB 适配器的天线很小，耳塞的天线更小，而你的头部还挡在耳塞与 PC 之间。到目前为止，大多数“连接不佳”的报告都归结为以下原因之一，每一项大约一分钟就能检查完。错误报告表单为每一项都设有复选框，请勾选你尝试过的项目。

{: .note }
请一次只改一项，每改一项都试听几分钟：如果断音消失，就找到了原因。

### 1. 关闭这台 PC 上的其他蓝牙适配器

BlueCaster 通过 USB 适配器串流时，Windows 自带的蓝牙（内置适配器）仍在旁边持续发射。两者共用一个频段，天线位置往往也很近。耳机在 PC 上的应用也通过内置适配器连接，这会让耳机多出第二条链路（见下一项）。请在 BlueCaster 运行期间，或至少在测试期间，在设备管理器中禁用内置适配器。BlueCaster 检测到其他正在使用的适配器时，会在主页上显示提示。

一位长期测试者指出，连接不稳定和编解码器切换不顺有两个原因，第二个正在使用的适配器就是其中之一。

### 2. 只给耳机一条连接

双设备（多点）连接让耳机可以同时连接手机和 PC。每条连接都会占用无线时间。开启多点连接时，有些耳机还会减少提供的编解码器、拒绝免提链路（因此看不到电量），或为另一台设备预留一个编解码器端点。耳机的配套应用也算在内：即使你只用它查看电量或调节均衡器，它也会通过手机或这台 PC 的蓝牙保持自己的链路。

测试方法：在耳机的应用中关闭双设备连接，关闭手机的蓝牙，退出手机和 PC 上的配套应用，然后从 BlueCaster 重新连接。

双设备连接正是那位测试者指出的另一个原因：断开配套应用之后，编解码器切换顺畅了许多。曾有一副耳机仍连着开启了 LE Audio 的手机，结果拒绝了首次连接。还有多款耳塞在手机或配套应用参与时，向 BlueCaster 提供的编解码器更少或比特率更低。Sony 耳机开启多点连接时会关闭 LDAC。

### 3. 移动适配器的位置

- 使用 **USB 2.0 端口**，或一条短的 USB 延长线。USB 3 端口和线缆会在 2.4 GHz 频段产生噪声，而且就在适配器旁边。
- **远离其他无线接收器**：游戏鼠标和键盘的接收器、无线耳麦接收器、Wi-Fi 天线。相邻端口上插着接收器，是出现这类症状的常见原因。
- **让适配器与耳机之间没有遮挡**。如果 PC 放在桌子下面，你和桌子挡在中间，信号会损失很多。用 USB 延长线把适配器引到桌面上，比其他任何办法都有效。

有一台 PC 没有 Wi-Fi 适配器，无法为 AFH 提供参考，游戏鼠标的接收器又插在适配器旁边。结果链路只能承载约 750 kbps，适配器把 79 个信道中最多 46 个标记为不良。另一例中，耳塞离适配器只有一米，信号仍然很弱，在接近比特率上限时每隔几分钟就会完全中断一次。

### 4. 让 2.4 GHz Wi-Fi 远离链路

把这台 PC 切换到 5 或 6 GHz Wi-Fi；如果可以，附近的手机和其他设备也一并切换。如果必须使用 2.4 GHz，BlueCaster 会让适配器避开这台 PC 的 Wi-Fi 所用的信道（AFH，自动）。如果 PC 没有 Wi-Fi 适配器、使用有线网络，或连接的频段与路由器的 2.4 GHz 网络不同，BlueCaster 就无法得知该信道。这时请查出路由器的信道（在路由器的管理页面查看，或用手机上的 Wi-Fi 分析应用），如果信道会自动切换，请在路由器上固定它，然后在**适配器 > 避开 Wi-Fi 信道 > 手动**中输入，例如 `6` 或 `11`。请参阅[链路质量与 AFH](usage#link-quality)。

在繁忙的 2.4 GHz 网络上，LDAC 990 kbps 在 5 分钟内丢失了约 1,700 个数据包。把路由器固定在一个信道，并将 AFH 设为“手动”、填入该信道后，15 分钟内只丢失了 33 个。

### 5. 给链路留出余量

蓝牙链路即使在理想条件下，也只能承载略高于 1 Mbps 的数据。LDAC 990 kbps、LHDC V5 900 和 1000 kbps 以及高 bitpool 的 SBC XQ 几乎不给重传留下余地。真无线耳塞还要把音频从一只转发到另一只，同样占用无线时间，因此即使链路干净，900 kbps 及以上对它们也很吃力。

- 试试 **ABR**（自适应比特率；LDAC、LHDC V5、aptX Adaptive，SBC 为自适应 bitpool），或降低一级：LDAC 660、LHDC V5 500、SBC XQ bitpool 29 到 36。
- 换用 **SBC 或 AAC**，看断音是否仍然存在。如果仍然存在，原因就不在比特率。
- 检查耳机本身：把耳机与手机配对，在手机上设置相同的编解码器和比特率，在同一位置试听。如果在手机上也断音，限制就在耳机一侧。

在一条只能承载 750 kbps 的链路上，高于 500 kbps 的设置都会断音，而 ABR 没有丢包。有一款廉价耳塞的 SBC 能力允许 bitpool 53，但 SBC XQ 的 bitpool 超过 36 就没有声音了。同一款耳塞上，LHDC V5 会随机断音，LDAC 却很稳定。干净的链路是能承载高比特率的：一台笔记本电脑的内置适配器以 LDAC 990 kbps 串流 5 分钟，丢失 0 个数据包。

### 6. 更新 BlueCaster

有几例听起来像无线问题的卡顿，其实是应用的错误。在 2.0.1 中，虚拟线缆送来的音频延迟时，应用会以快于实时的速度发送，听起来就是一秒有声、一秒无声；执行“断开连接 > 连接”后，音频会一直卡顿，直到重启应用；睡眠、长时间运行或多次重启之后，过时的蓝牙堆栈会拒绝连接。这些问题都已在当前版本中修复（[更新](usage#updates)）。如果更新后问题消失，就无需报告。

## 解读链路质量 {#link-quality}

**诊断 > 链路质量**（以及主页上的图表）可以告诉你问题出在无线、PC 还是应用。请在问题发生时截图，并附在报告中。

| 看到的现象 | 含义 | 指向 |
|:--|:--|:--|
| **信号（与理想值之差）**远低于 0（约 -25 dB 或更低） | 适配器收到的耳机信号远低于理想范围。这不是绝对电平：0 为理想值，-30 表示比理想值低 30 dB，因此 -30 仍能播放，但已没有余量 | 无线：距离、你的头部和身体、适配器的摆放位置 |
| **发送队列**已满，**发送前丢弃的数据包**持续增加，比特率低于编解码器的比特率 | 数据包等待发送的时间过长；链路当前无法承载这一比特率 | 无线或干扰，或比特率过高 |
| **跳频（AFH）**跳动不定，或在丢包的同时停在 79 | 适配器把出错的信道标记为不良；停在 79 表示适配器已无法区分好坏 | 干扰：Wi-Fi、其他接收器、第二个蓝牙适配器 |
| **捕获时丢弃的音频**持续增加，主页显示**电脑繁忙** | PC 没有及时提供音频 | PC：负载、捕获设备、虚拟线缆 |
| 各项都平稳无异常，却仍有无声或卡顿 | 链路正常，PC 上也没有丢弃任何数据 | 应用或耳机的解码器：请附上诊断包报告 |

PC 无法看到接收端的情况。要测量实际收到的内容，可以用[对端接收器测试](usage#receiver)，让一台 Linux PC 代替耳机接收。

## 由耳机决定的事 {#headphones}

有些“只有 400 kbps”或“没有 LDAC”的报告与链路完全无关：耳机会告诉 BlueCaster 自己接受哪些编解码器和比特率，BlueCaster 和 Android 一样照此执行。日志行 `remote supports ...` 显示了耳机提供的内容。

- **Huawei FreeBuds** 只有在其 AI Life 应用设置了“优先音质”并关闭多设备连接之后，才会向 PC 提供 LDAC；否则只列出 SBC 和 AAC。自 2.0.2 起，如果关闭自动选择并选择 LDAC，BlueCaster 会自动请求该模式。
- **LHDC V5 耳机**会通告一个最大比特率。一款耳机在其应用的 96 kHz 模式下列出 400 kbps，在 192 kHz 模式下为 1000 kbps。OPPO Enco Free4 和 Enco X4 无论应用如何设置，向 PC 列出的都是 400 kbps 和 48 kHz。在关闭 ABR 的情况下串流 LHDC V5 时，2.0.2 会通过 OPPO 耳塞自己的协议请求 Hi-Res，并重新连接一次使其生效（尚未在真实耳塞上确认）。
- **ABR** 会把 LHDC V5 保持在 400 kbps 或以下，与 Android 一样。
- 耳机**为另一台设备保留**的编解码器，在那台设备连接期间不会出现（[耳机同时连接其他设备时缺少编解码器](usage#sep-in-use)）。

如何查看耳机提供的内容：[查看耳机提供的编解码器](usage#codec-fallback)。

## 连接失败 {#connecting}

主页上的错误信息会说明发生了什么；[连接超时](usage#connection-timeouts)中的表格解释了每条消息。与无线有关的情况如下：

- **设备无应答**（Page Timeout）：设备已关机、超出范围、首次连接时未进入配对模式，或者适配器仍在运行 ROM 固件。没有加载固件的 Realtek 适配器扫描不到任何设备，每次连接都会超时，或者能正常打开却始终无法串流。曾有一个固件文件其实是另存下来的网页。适配器页面会显示固件是否已加载。
- **连接已建立但没有传输任何数据**：无线环境不佳，或者耳机正忙于另一台设备。请重试，或移动适配器的位置。
- **身份验证失败**，或日志显示 `signaling connection failed (0x66)`：耳机保留了以前配对时的密钥，通常来自这台 PC 上 Windows 自带的蓝牙。`(0x67)`：耳机正忙于另一台设备，例如开启了 LE Audio 的手机。请断开其他设备，在耳机的应用中关闭 LE Audio，让耳机进入配对模式并连接一次；之后的连接会使用保存的密钥。
- 断开连接后耳机**无法连接手机**：自 2.0.2 起，断开连接会释放链路。如果你靠关机再开机让耳机在 PC 和手机之间切换，请关闭**自动重新连接**。

## 报告最终查明的原因 {#reports}

迄今为止所有与无线相关的报告，按最终查明的原因分组。

| 原因 | 报告数 | 示例 |
|:--|:--|:--|
| **环境**：无线、摆放位置、另一台设备 | 约三分之一 | 同信道的 2.4 GHz Wi-Fi、适配器旁边的游戏鼠标接收器、第二个正在使用的蓝牙适配器、双设备连接和运行中的配套应用、真无线耳塞上比特率没有余量、小型耳塞信号弱、固件文件其实是另存的网页 |
| **耳机**：耳机向 PC 提供的内容 | 约四分之一 | 只有在 Huawei 的音质模式下才有 LDAC、LHDC V5 被耳机自身的模式限制在 400 kbps、需通过 OPPO 的协议设置 Hi-Res、编解码器被手机占用 |
| **应用**：BlueCaster 的错误，均已修复 | 不到一半 | 使用虚拟线缆时音频发送快于实时、“断开连接 > 连接”后卡顿、睡眠或多次重启后蓝牙堆栈过时、断开连接后链路仍被保留、主动发起连接的耳机被误判为密钥错误、编解码器缓存导致 LDAC 不显示、适配器未被识别（某款芯片、某个 USB 类、尚未生效的驱动程序绑定） |

值得注意的几点：

- **卡顿和断音的原因大约一半在应用**（2.0.1 和最早几个 2.0.2 beta 版本中的时序错误），**一半在环境**。经过测量的两例干扰情况表现相同：发送比特率降到 550 到 800 kbps，发送队列填满，适配器的信道图变为 79 / 79。
- **连接问题大多出在应用**，而且几乎都发生在同一种情形：耳机开机后自己发起连接。蓝牙模拟器无法重现这种情形，因此这些修复依赖用户提供的日志。
- **“缺少编解码器”和“比特率上不去”取决于耳机**向 PC 提供什么，通常由配套应用的设置决定。
- 有些问题**看起来像无线问题，其实不是**：某个型号使用 AAC 时无声（帧格式问题）、耳机关机后 Windows 输出仍停留在虚拟线缆上、切换编解码器重新连接期间扬声器会响几秒、有线耳机也有声音（捕获 Windows 默认输出时本来就是这样）。

## 报告 {#reporting}

如果上述检查没有找到原因，请提交[错误报告](https://github.com/SeiyaFunaokaJP/BlueCaster/issues/new?template=bug_report.yml)，并勾选你尝试过的项目。提供以下内容有助于快速解决无线问题：

1. 在**诊断 > 报告问题**中，将**详细日志**设为**详细（debug）**，然后重现问题。
2. **诊断包**（开启**包含 HCI 抓包**后选择**诊断包 > 保存…**，然后**在 GitHub 上报告**）。诊断包中有串流状态记录（发送队列、丢弃的数据包、信号、AFH 信道随时间的变化）和失败连接的 HCI 抓包，能看出数据包在哪一步中断。
3. 问题发生时的**链路质量截图**。
4. 使用 **SBC 或 AAC** 以及**更低的比特率**时是否同样发生。
5. 你对表单中“双设备连接”“另一个蓝牙适配器”和“Wi-Fi”几个问题的回答。
